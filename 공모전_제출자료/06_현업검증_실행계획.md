# 현업 검증 실행계획

작성: 2026-09-13. 현업 인터뷰와 파일럿은 아직 수행하지 않았다.

## 첫 검증 범위

협력사·제조사의 PDF 사양서와 내부 XLSX 부하 목록 사이에서 모터의 정격출력·정격전압·주파수 변경 반영이 누락되는지 검토한다. 동일 TAG라도 항목 의미·운전 조건이 다르면 비교하지 않는다. 변경 누락 확정에는 문서 개정과 승인 상태 확인이 필요하다.

## 외부 근거와 한계

- [NRC Palisades 2008, Event 44645](https://www.nrc.gov/reading-rm/doc-collections/event-status/event/2008/20081110en): 별도 계산에서 증가한 팬 모터 부하가 발전기 부하 계산에 반영되지 않아 특정 조건의 과부하 가능성이 보고됐다. 실제 사고 발생을 뜻하지 않는다.
- [NRC Davis-Besse 2001, PDF 12쪽](https://www.nrc.gov/cdn/legacy/reactors/operating/oversight/reports/davi_2001014.pdf): 부하 증가가 도면과 보고서에는 반영됐지만 관련 전기 계산에는 누락됐다.
- [Hexagon Smart Engineering Integrity](https://bynder.hexagon.com/m/124fac5d55dc4a27/original/Hexagon_PPM_10_Example_Rules_SEI_White_Paper_US_2018.pdf): 공종 간 및 외부 스프레드시트의 규칙 검증 기능이 있다.
- [AVEVA Compare/Update](https://help.aveva.com/AVEVA_Everything3D/2.1/AIDUUG/AIDUUG14.html): 데이터 소스 간 객체 연결과 속성 차이 검출 기능이 있다.

문제의 존재는 확인됐지만 오래된 해외 사례로 국내 발생 빈도나 비용을 추정하지 않는다. 공급업체 자료는 경쟁 기능의 근거이며 독립적인 효과 측정은 아니다. 통합 시스템 밖 PDF/Excel 검토의 미충족 수요는 아직 가설이다.

## 인터뷰 — 실무자 3~5명, 각 20~30분

전기 설계자, 기계/벤더 문서 검토자, 검토 책임자를 대상으로 현재 업무부터 듣고 마지막에 제품 예시를 보여준다. 연락은 아직 하지 않았다.

1. 최근 프로젝트에서 어느 단계의 어떤 문서를 비교했나요?
2. 실제 불일치 또는 변경 누락 사례 하나를 설명해 주세요. 어느 문서·항목·개정이었나요?
3. 누가 어떤 방법으로 발견했고 원문 확인과 판단에 얼마나 걸렸나요? 기록이 있나요?
4. 정상적인 차이였나요, 실제 수정이 필요했나요? 판단 기준은 무엇인가요?
5. 현재 도구가 자동 검사하는 범위와 사람이 다시 확인하는 부분은 무엇인가요?
6. 재검토·수정·재작업 중 실제 발생한 후속 조치는 무엇인가요?
7. 최근 프로젝트 몇 건 중 몇 건에서 발생했나요? 기억과 기록을 구분해 주세요.
8. 제품 예시를 보면 추가로 해야 할 확인 업무는 무엇인가요?
9. 익명화 문서로 시간 비교가 가능한가요? 문서 이용과 AI 처리 허용 범위는 무엇인가요?

응답자별 기록 양식:

| 항목 | 기록 |
|---|---|
| 익명 ID / 역할 / 일자 | 미기록 |
| 프로젝트 유형 / 검토 단계 | 미기록 |
| 문서 종류 / TAG / 항목 / 개정 | 미기록 |
| 최근 사례 / 발견 방법 / 실제 조치 | 미기록 |
| 기존 도구 / 남는 수작업 | 미기록 |
| 빈도·소요 시간 / 기록 또는 추정 | 미기록 |
| 문서 제공·처리 가능 범위 | 미기록 |
| 제품 가설을 반박하는 응답 | 미기록 |

## 파일럿과 정답셋

1. 사용 가능한 익명화 PDF/XLSX 한 묶음을 확보한다. 개발용과 평가용을 분리한다. 평가용을 보고 규칙을 고쳤다면 새 평가 묶음이 필요하다.
2. 엔지니어가 문서 번호·개정·승인 상태·항목 의미를 확인하고 정답을 먼저 작성한다. 최신 업로드를 최신 승인본으로 간주하지 않는다.
3. 불일치 외에 정상 일치, 단위만 다른 일치, 정상적인 조건 차이, 이전 개정, 읽기 어려운 값을 포함한다. 합성 오류와 자연 발생 사례는 별도 집계한다.
4. 수작업과 AI 지원의 동일한 검토 완료 범위를 측정한다. 준비·추출 수정·오탐 처리·근거 확인·판단 기록을 포함하며 작업자 시간과 시스템 대기는 분리한다.
5. 누락·오탐·근거 위치 오류를 엔지니어와 확인한다. 분석 실패 문서를 평가에서 조용히 제외하지 않는다.

케이스별 기록 양식:

| 항목 | 기록 |
|---|---|
| 케이스 ID / 자연 발생 또는 합성 | 미기록 |
| TAG / 항목 의미 / 운전 조건 | 미기록 |
| 문서 A 번호·개정·상태·위치·값·단위 | 미기록 |
| 문서 B 번호·개정·상태·위치·값·단위 | 미기록 |
| 기대 결과: 일치/불일치/비교 불가/추출 확인 필요 | 미기록 |
| 정상 차이 또는 조치 필요 / 근거 / 검토자 | 미기록 |
| 시스템 결과 / TP·FP·FN 또는 해당 없음 | 미기록 |
| 근거 위치 정확 여부 / 실패 원인 | 미기록 |

정밀도=TP/(TP+FP), 재현율=TP/(TP+FN). 분모 0은 N/A다. 판정 단위는 TAG+항목 의미+비교 문서/개정 조합이다. 비교 불가와 추출 확인 필요는 별도 집계한다. 시간 절감률=(수작업 총시간-AI 지원 총시간)/수작업 총시간×100. 동일인이 같은 문서를 반복하면 학습 효과가 있으므로 동등한 묶음의 순서를 교차 배정하거나 한계를 기록한다.

## 현재 구현 격차 — 정적 코드 검토

이번에는 서비스를 실행하거나 AI 성능을 재측정하지 않았다.

| 코드 | 확인 내용과 다음 작업 |
|---|---|
| `backend/app/services/extraction_pipeline.py` | 실제 추출 저장 경로가 있다. API 미설정 시 추출을 건너뛴다. 파싱과 설비 추출 성공을 구분해야 한다. |
| `backend/app/db/models.py` | 문서 개정·승인 상태, 값의 운전 조건·항목 의미 구분 필드가 없다. 비교 자격 판단을 위한 모델이 우선이다. |
| `backend/app/services/crosscheck_basic.py` | 항목 그룹과 단위 비교는 있다. 다른 차원도 mismatch로 처리하고 전역 1% 허용오차를 쓴다. 비교 불가와 항목별 기준이 필요하다. |
| `backend/app/services/issue_rules.py` | 영향 항목은 고정 IMPACT_MAP이다. 프로젝트별 연결을 추적한 영향분석으로 주장하지 않는다. |

구현 순서: 문서/값 문맥 모델 → 비교 가능 여부와 상태 분리 → 근거 확인 UI → 독립 평가.

## 진행 판단

- 진행: 독립적인 실무자들이 구체적인 잔여 업무를 확인하고 문서를 확보할 수 있으며, 같은 검토 품질에서 전체 시간이 줄어든다.
- 범위 수정: 주요 문제가 승인본 식별·벤더 변경 추적이면 그 업무를 우선한다.
- 재검토: 기존 도구로 충분하거나 문서를 확보할 수 없거나 결과 확인 비용이 수작업보다 크다.

수치 합격 기준은 파일럿 전에 담당자와 정한다. 소규모 샘플 100%를 현업 전체 정확도로 발표하지 않는다.
