# 발표 스토리라인 — 설계문서 교차검증 에이전트

> 하이맥 AI 활용 공모전 · 카테고리 ① 설계·엔지니어링 (설계·계산·검토 업무 혁신)
> 한 줄 정의: **여러 설계 문서에 흩어진 동일 설비의 정보를 AI가 교차 검증하여, 문서 간 불일치와 영향 가능 항목을 찾아주는 엔지니어링 검토 지원 시스템**

---

## 0. 엘리베이터 피치 (30초)

상세설계 단계에서 하나의 설비(예: 펌프 P-101)의 정보는 기계 사양서(PDF), 전기 부하계산서(Excel), 단선결선도(도면), 설비 목록 등 **대여섯 종류의 문서에 흩어져** 있습니다.
이 값들이 서로 맞는지는 지금도 엔지니어가 문서를 나란히 펼쳐 **눈으로 대조**합니다. 문서가 수백 장이면 피로가 쌓이고, 숫자 하나(정격출력 15 → 18.5 kW)를 놓치면 케이블·차단기 산정이 틀어져 **현장 재시공**으로 이어집니다.
우리 시스템은 이기종 문서에서 **같은 설비의 같은 항목을 자동으로 연결**하고, 값이 어긋난 지점과 그것이 **영향을 줄 후속 설계 항목**을 근거와 함께 제시합니다. 판정은 사람이 아니라 규칙 기반 검증 엔진이 하므로, AI가 숫자를 지어내지 않습니다.

## 1. 업무 현안 적합성 (배점 20)

### 3대 페인포인트

| # | 페인포인트 | 현재 실태 | 결과 리스크 |
|---|---|---|---|
| 1 | **이기종 문서 간 데이터 파편화** | 동일 TAG(M-101)의 정보가 PDF·Excel·도면에 분산, 통합 관리 불가 | 부서 간(기계·전기·배관) 값이 따로 관리되어 정합성 확인이 사람 손에 달림 |
| 2 | **치명적 휴먼 에러** | 수백 장 문서를 엔지니어가 직접 눈으로 대조 → 피로 누적 → 숫자 오기재 | 정격출력 불일치 → 하위 케이블 규격·차단기 용량 산정 오류 |
| 3 | **연쇄 파급의 사각지대** | 설비 스펙 하나가 바뀔 때 어떤 후속 항목이 영향받는지 사람이 일일이 추적 | 시공 오류, 안전 리스크, 준공 지연 |

### 왜 지금 풀어야 하나
- 도면 검토 / 설계 심의 / IDC(Inter-Discipline Check)는 EPC·상세설계의 **공식 산출물**이지만 대부분 수작업이다.
- 계산(ETAP 등)·모델링(BIM)에는 도구가 있으나, **문서들 사이의 정합성 대조**는 도구 공백 구간이며 에러율이 가장 높다.

> 🔴 **발표 시 보강 필요**: 사내 재시공/설계변경 사례 1건, 또는 현업 엔지니어 1~2명 인터뷰 한 줄. "선제적 방어"의 설득력이 크게 올라감.

## 2. 창의성·독창성 (배점 25 — 최고 배점)

### 기존 방식과 무엇이 다른가

| | 기존 수작업 | 기존 자동화 (OCR + 규칙) | **우리 접근** |
|---|---|---|---|
| 문서 통합 | 사람이 문서를 나란히 펼침 | 정형 양식만, 포맷 바뀌면 실패 | **비정형·이기종 문서를 LLM이 이해해 TAG 기준으로 연결** |
| 언어/표기 차이 | 사람이 "정격출력=Rated Output=kW" 판단 | 문자열 일치만 → 매칭 실패 | **의미 기반 정합** (정격출력 = RATED OUTPUT = Power(kW)) |
| 검토 흐름 | 문서를 처음부터 끝까지 훑음 | 규칙에 걸린 것만 리스트 | **불일치가 먼저 엔지니어에게 온다** (exception-driven review) |
| 신뢰성 | 사람 판단 | 규칙 범위 밖은 사각지대 | **AI는 추출만, 수치 판정은 결정론적 엔진** — 환각 차단 |
| 추적성 | 근거를 사람이 다시 찾음 | 위치 정보 없음 | **모든 발견에 원문 위치·문장 첨부** → 현업이 즉시 검증 |

### 3가지 독창 포인트 (발표에서 강조)
1. **이기종·다국어 시맨틱 정합** — 규칙엔진이 못 하던 "같은 뜻 다른 표기"를 LLM으로 해결. (데모: 한글 사양서 + 영문 도면 + Excel을 한 표로)
2. **검토 프로세스 재설계** — "문서를 검토한다"에서 **"이슈를 판단·승인한다"**로. 엔지니어의 시간을 대조가 아니라 의사결정에 쓰게 함.
3. **AI/결정론 분리 아키텍처** — LLM에게 판단까지 맡기는 여느 AI 앱과 반대로, 신뢰가 필요한 계산은 코드가 한다. → "믿고 쓸 수 있는 AI"

## 3. AI 활용 적절성 (배점 15)

### AI가 하는 일 / 하지 않는 일

| 단계 | 담당 | 이유 |
|---|---|---|
| 문서 내용 이해, 설비 TAG 식별, 값 추출 | **AI (Gemini)** | 비정형·다국어 문서 이해는 LLM만 가능 |
| 단위 환산, 수치 비교, 일치/불일치 판정 | **검증 엔진 (결정론 코드)** | 정확·재현 가능해야 하며 환각 위험 배제 |
| 심각도(높음/중간/낮음/참고) 분류 | **규칙 테이블** | 설계 기준은 고정 규칙으로 관리 |
| 왜 중요한지 설명 (근거 문장) | **AI** | 사람이 읽기 쉬운 서술만, 판단은 안 함 |
| 최종 조치 결정, 설계 확정 | **담당 엔지니어** | 시스템은 승인하지 않음 |

- AI를 **꼭 필요한 곳에만** 씀 → "기술 과시용 AI"가 아님을 명확히.
- API 키가 없어도 결정론 파트는 그대로 동작 (graceful degradation).

## 4. 활용성·기대효과 (배점 20)

### 적용 범위
- **분야**: 전기·기계·배관·계장 전 공종. 공정별로는 상세설계 → 설계검토 → 구매사양 확정 단계.
- **재사용성**: 프로젝트마다 반복. 같은 엔진에 파서만 추가하면 CAD·BIM·스캔 도면으로 확장.
- **확산**: 현장/프로젝트 독립적. 사내 표준 검토 툴로 배치 가능.

### 기대효과 (정량 모델 — `03_실현가능성_벤치마크.md` 참조)
- 설계검토 1회 = 설비 N대 × 문서 M종 × 항목 P개 수동 대조 → AI 선별 후 엔지니어는 **발견 이슈 K건만 판단**.
- 정량 산정은 사내 실제 프로젝트 규모를 대입해 확정 (템플릿 제공).
- 재시공 1건 예방 시 기대 절감액이 도입 비용을 상회 (건설 재작업은 통상 프로젝트 원가의 상당 비중).

## 5. 실현가능성·구체성 (배점 20)

- **구동하는 풀스택 프로토타입**: 백엔드(FastAPI) + 프론트(Next.js) + 실제 Gemini 연동. PDF·Excel·CSV·이미지 파싱.
- **실측 벤치마크 있음**: 현실적 샘플 문서 4종에 대해 초기 정확도 → 정규화 이슈 2건 발견·수정 → 재실행 시 오탐 0. (상세: `03_실현가능성_벤치마크.md`)
- **운영 로드맵 있음**: MVP → 파일럿 → 운영 단계별 필요사항을 솔직하게 정리.
- 데모/실사용 데이터가 화면에서 명확히 구분됨 (실제 분석인 것처럼 표시하지 않음).
